En el Modelo Tradicional, las acciones del usuario en la página (pinchar en un
botón, seleccionar un valor de una lista, etc.) desencadenan llamadas al servidor. Una
vez procesada la petición del usuario, el servidor devuelve una nueva página HTML al

la página con los cambios solicitados.

===== PAGINA 11 (960.00 x 540.00) =====
AJAX mejora completamente la interacción del usuario con
la aplicación, evitando las recargas constantes de la página,
ya que el intercambio de información con el servidor se
produce en un segundo plano.
Elimina la recarga constante de páginas mediante la
creación de un elemento intermedio entre el usuario y el
servidor. La nueva capa intermedia de AJAX mejora la
respuesta de la aplicación, ya que el usuario nunca se
encuentra con una ventana del navegador vacía esperando
la respuesta del servidor.

===== PAGINA 13 (960.00 x 540.00) =====
La historia de AJAX está íntimamente relacionada con un objeto de
programación llamado XMLHttpRequest. El origen de este objeto se
remonta al año 2000, con productos como Exchange 2000, Internet
Explorer 5 y Outlook Web Access (OWA).
Durante el desarrollo de OWA, se evaluaron dos opciones: 
un cliente formado sólo por páginas HTML estáticas que se 
recargaban constantemente 
un cliente realizado completamente con HTML dinámico o 
DHTML.
Sin embargo, para ser realmente útil a esta última le faltaba un 
componente esencial: "algo" que evitara tener que enviar 
continuamente los formularios con datos al servidor.   De aquí surge 
la primera versión de lo que denominó XMLHTTP
AJAX

===== PAGINA 14 (960.00 x 540.00) =====
Las páginas creadas dinámicamente mediante peticiones sucesivas AJAX, no son registradas de
forma automática en el historial del navegador, así que haciendo clic en el botón de "volver" del
navegador, el usuario no será devuelto a un estado anterior de la página, en cambio puede volver
a la última página que visitó. Soluciones incluyen el uso de IFrames invisible para desencadenar
cambios en el historial del navegador .
Los motores de búsqueda no analizan JavaScript. La información en la página dinámica no se
almacena en los registros del buscador. Exceptuando Google, que desde el 2011 sí indexa
contenido Ajax y JavaScript (pero no es eficiente aún su indexación ya que puede tardar en
hacerlo. https://developers.google.com/search/docs/advanced/guidelines/ajax-faqs?hl=es)
Hay problemas usando Ajax entre nombres de dominios, a esto se le conoce como Same Origin
Policy o Política del Mismo Origen, lo cual es una medida de seguridad que puede ser solucionada
con Cross-Origin Resource Sharing (CORS). (esta técnica es firmando los scripts pero la mayoría de
los script no son firmados y además, Internet Explorer versión 11 e inferiores no soporta script
firmados).
AJAX - Consideraciones

===== PAGINA 15 (960.00 x 540.00) =====
Además con los nombres de dominio, por razones de seguridad, los navegadores modernos
no permiten el acceso a través de dominios . Esto significa que tanto la página web y el
archivo XML que intenta cargar, deben estar ubicados en el mismo servidor (al menos que los
se utilice CORS).
Dependiendo de como se desarrolle el sitio web, puedes mejorar o empeorar la carga en el
servidor. Ajax puede ayudar al servidor a evitar la fase de renderización de HTML, dejándole
ese trabajo al cliente, pero también puede sobrecargar al servidor si se hace varias llamadas a
Ajax.
Es posible que páginas con Ajax no puedan funcionar en teléfonos móviles, PDA u otros
aparatos. Ajax no es compatible con todos los software para ciegos u otras discapacidades.
AJAX - Consideraciones

===== PAGINA 20 (960.00 x 540.00) =====
La Primera Aplicación (cont)
Después de preparar la aplicación para la respuesta del servidor, se
realiza la petición HTTP al servidor:
peticion_http.open('GET', 'http://localhost/prueba.txt', true);

Las instrucciones anteriores realizan el tipo de petición más sencillo que se
puede enviar al servidor. En concreto, se trata de una petición de tipo GET
simple que no envía ningún parámetro al servidor. La petición HTTP se crea
mediante el método open(), en el que se incluye el tipo de petición (GET),
la URL solicitada (http://localhost/prueba.txt) y un tercer parámetro indica
asíncrono: True (asíncrono) o false (síncrona)

===== PAGINA 21 (960.00 x 540.00) =====
¿Método Get ométodo Post?
¿Método Get o método Post?
GET es más simple y más rápido que POST, y se puede utilizar en la mayoría de los 
casos.
Sin embargo, siempre use las peticiones POST cuando:
Debiera actualizar un archivo o una base de datos del lado del servidor
Se envío de una gran cantidad de datos al servidor (POST no tiene limitaciones de 
tamaño).
Envío de entrada del usuario (que puede contener caracteres desconocidos), POST 
es más robusto y seguro que el GET.

===== PAGINA 22 (960.00 x 540.00) =====
Asíncrono ¿true o false?
Mediante el envío de forma asíncrona (true), el código JavaScript no tiene que
esperar a la respuesta del servidor, sino que puede ejecutar otros scripts a la espera
de respuesta del servidor.
El envió con False no es recomendable porque si el servidor es lento no se le
permitirá seguir la ejecución del javascript hasta que la respuesta esté lista. Si el
servidor tarda demasiado esta función se puede colgar o dejar de ejecutar.
